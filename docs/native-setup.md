# Native setup

The Expo config plugin covers most of this automatically:

```json
{ "plugins": [["@signalwire/react-native", { "enableCallKit": true, "enableVoipPush": true }]] }
```

Bare React Native projects apply the same changes by hand — see the tables below.
The VoIP push section applies to **bare React Native only**. Expo projects
get that file generated by the config plugin — see
[`push-setup.md`](push-setup.md#1d-the-native-pushkit-hook--generated-for-you).

## iOS: reporting a VoIP push before JavaScript boots

On a cold start the JS bundle is not running when a VoIP push arrives, and iOS
terminates the app if CallKit is not told about the call almost immediately.
Report it from native code.

Use the source the Expo plugin generates, `SignalWireVoipPush.m`, rather than
writing your own `pushRegistry:didReceiveIncomingPushWithPayload:` handler.
Expo generates a Swift `AppDelegate`, and Swift cannot import RNCallKeep
(callkeep#856), so the file is an Objective-C category instead of a patch to
that file; it works unchanged in a bare app. It does more than report the call,
and the package depends on all of it:

- it forwards every payload key beyond `uuid`, `call_id`, `from` and
  `from_name` to JavaScript. A bridge topology's single-use `bridgeToken`
  travels this way; without it an answered push has nothing to dial and the
  caller stays parked until the call times out as missed;
- it caches the PushKit token and each push until JavaScript has seen it, which `watchVoipToken` and
  the cold-start adoption in `getCallKit().setup()` read. iOS issues both
  before JavaScript has a bridge, so without the cache the first install
  registers no device and a call answered on a cold start has no entry to
  land on.

[push-setup.md §1d](push-setup.md#1d-the-native-pushkit-hook--generated-for-you)
shows how to write it out of `voipPushSource.ts` as an `.m` and add it to the
app target's Compile Sources.

Your push payload **must** include the SignalWire `call_id`. `CallKeepBridge`
picks the reported call up from callkeep's `didDisplayIncomingCall` event by
itself and hands it to `CallRegistry`, which fuses the native entry with the
SDK call by that id. Add no `didDisplayIncomingCall` listener of your own that
calls `reportIncomingPush`: callkeep emits the event for the calls
`reportIncomingPush` reports too, so each one would be reported again, without
end.

## iOS: calling back from Recents and Siri

Calls placed or answered through CallKit are listed in the Phone app's
Recents (`includesCallsInRecents`, default `true` in `getCallKit().setup()`;
pass `false` to keep them out). Tapping one, or asking Siri to call back,
opens the app with an `INStartCallIntent` user activity. callkeep turns it
into a start-call event only if the app delegate passes it on, so the plugin
(with `enableCallKit`, the default) generates `SignalWireCallKitActivity.m`:
an Objective-C file that wraps the AppDelegate's
`application:continueUserActivity:restorationHandler:` and hands call intents
to `[RNCallKeep application:continueUserActivity:restorationHandler:]`. The
AppDelegate's own handling (universal links, Expo's subscribers) still runs.
It also adds the three call intents to `NSUserActivityTypes`.

The app then dials from `startCallRequested$`:

```ts
getCallKit().startCallRequested$.subscribe(({ handle, video }) => {
  void dial(handle, { audio: true, video });
});
```

A call-back that launches the app arrives before React mounts; it is held for
the first subscriber for up to a minute. Under the UIScene lifecycle the scene
delegate must pass `scene(_:continue:)` and the connection options' user
activities to the app delegate (the example's does). Bare projects: copy
`packages/react-native/src/plugin/callKitActivitySource.ts` into the app
target, or call RNCallKeep from your own Objective-C AppDelegate.

## iOS: Info.plist

Applied by the plugin. The usage strings come from the plugin's
`microphonePermission` / `cameraPermission` options, else from what the app
already sets (`ios.infoPlist`, or another plugin), else a generic default.
For bare projects:

| Key | Value |
| --- | --- |
| `NSMicrophoneUsageDescription` | Why your app needs the microphone |
| `NSCameraUsageDescription` | Why your app needs the camera |
| `UIBackgroundModes` | `audio` (always), plus `voip` when using VoIP push |
| `NSUserActivityTypes` | `INStartCallIntent`, `INStartAudioCallIntent`, `INStartVideoCallIntent` (Recents and Siri call-backs) |

Enable the **Push Notifications** capability and, for VoIP push, the
**Voice over IP** background mode in Xcode.

What the plugin applies (`src/plugin/withAndroidCallKit.ts`). For bare projects:

```xml
<uses-permission android:name="android.permission.RECORD_AUDIO" />
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.MODIFY_AUDIO_SETTINGS" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MICROPHONE" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.WAKE_LOCK" />
<uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />

<!-- Native call UI only -->
<uses-permission android:name="android.permission.MANAGE_OWN_CALLS" />
<uses-permission android:name="android.permission.READ_PHONE_STATE" />
<uses-permission android:name="android.permission.READ_PHONE_NUMBERS" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_PHONE_CALL" />

<application>
  <!-- callkeep's ConnectionService. android:permission is a guard (only
       Telecom may bind it), not something the app can hold: never add
       BIND_TELECOM_CONNECTION_SERVICE as a uses-permission. Declare no
       foreground-service type without its FOREGROUND_SERVICE_* permission
       (no "camera"): Android 14+ refuses the whole service. -->
  <service
    android:name="io.wazo.callkeep.VoiceConnectionService"
    android:label="Calls"
    android:permission="android.permission.BIND_TELECOM_CONNECTION_SERVICE"
    android:foregroundServiceType="phoneCall|microphone"
    android:exported="true">
    <intent-filter>
      <action android:name="android.telecom.ConnectionService" />
    </intent-filter>
  </service>
</application>
```

The package's own Android library (the incoming-call notification, with
`USE_FULL_SCREEN_INTENT`, and the reader of a call's Telecom audio routes) is
autolinked; its manifest merges into the app's.

## Android: waking on a data message

FCM data messages reach a killed app through a headless task, and a running app
through a foreground handler; Android never delivers to both. Register both
from your entry file, alongside your root component, not inside it:

```js
// index.js, after the polyfills import
import { getCallKit, registerAndroidCallPush } from '@signalwire/react-native/callkit';

void getCallKit().setup({ appName: 'My App' });
registerAndroidCallPush();   // no-op on iOS and without Firebase installed
```

`registerAndroidCallPush()` wires `setBackgroundMessageHandler` and `onMessage`,
maps the sender's `sw_`-prefixed keys back (`sw_from` → `from`; FCM rejects a
data key named `from`), reports the call with every other payload key passed
through as `data` (where a bridge topology's `bridgeToken` travels), and brings
the app forward. A hand-written handler has to do all four; see
[push-setup.md §2d](push-setup.md#2d-handle-the-push).

**Android 14+ restricts starting a foreground service from the background.** For
the locked-device case, present the call with a full-screen intent
(`USE_FULL_SCREEN_INTENT`) rather than relying on a foreground service start;
callkeep's self-managed ConnectionService mode handles this when configured.

## Choosing a push vendor

For the step-by-step build, see [push-setup.md](push-setup.md).

**SignalWire has no push infrastructure.** It will not send the push for you and
there is no device-token registration endpoint. The full chain is yours:

```
SignalWire  --webhook-->  your backend  --push-->  device
                                                     |
                                          reportIncomingPush({ callId, ... })
                                                     |
                                              CallRegistry fuses it
                                              with the SDK call
```

Your backend has to learn an inbound call is coming (a webhook), map the callee
to a stored device token, and send the push itself. The push payload **must**
carry the SignalWire `call_id`.

### The filter that matters

iOS VoIP pushes go through **PushKit**: a different topic (`<bundle-id>.voip`),
an `apns-push-type: voip` header, and the only push type that wakes a killed app
for a call. Most "unified push" services only speak standard APNs alerts. FCM is
genuinely cross-platform for normal notifications but **cannot send PushKit
pushes** — its iOS path is standard APNs alert/background. Architecting around
"FCM everywhere" works until iOS, then stops.

### Vendor comparison

Checked August 2026 against vendor documentation. Verify before committing —
these change.

| Vendor | iOS VoIP (PushKit) | Notes |
| --- | --- | --- |
| **Roll your own** (`.p8` + `node-apn` + FCM) | Yes | One `.p8` auth key covers both alert and VoIP push types. An APNs VoIP send is an HTTP/2 POST with a JWT — on the order of 50 lines. |
| **AWS SNS** | Yes | APNs VoIP platform applications; `.p8` token auth or `.p12` cert. Unifies iOS VoIP and FCM behind one API. The most credible off-the-shelf option. |
| **OneSignal** | Yes, partially | See caveats below. No Android VoIP. |
| **Courier** | Not documented | Orchestration layer over other providers; no `apns-push-type: voip` or `.voip` topic override in its APNs surface. Treat as unsupported pending confirmation from their support. |
| **Expo Push Notifications** | No | Explicitly unsupported. Fine for everything else. |
| **FCM alone** | No | Cannot send PushKit pushes. Android half only. |

### OneSignal specifics

Their documentation is explicit that it does **not** remove the PushKit work:

> OneSignal does not handle VoIP token registration. You are responsible for
> registering VoIP tokens in your app using Apple PushKit.

Also required:

- **A separate OneSignal app** for VoIP. One OneSignal app supports one
  certificate type, so you run two: standard push and VoIP-only.
- **A VoIP Services `.p12` certificate**, not your standard APNs push
  certificate. Upload the wrong one and "the API will accept your push request
  but Apple will reject it and the notification will never arrive."
- **`"test_type": 1` when registering sandbox tokens.** Omitting it fails
  silently: the API call succeeds and returns no error, but Apple treats the
  token as production and drops every push.
- **No Android VoIP.** OneSignal's own guidance is data-only pushes plus a
  foreground service and custom call UI — which is the path `CallKeepBridge`
  already implements, so nothing is gained there either.

### Recommendation

Because every option still leaves the PushKit registration and the native
hook in the app (this package generates them, `SignalWireVoipPush.m`), and
because the Android half is plain FCM data messages regardless, the unification
on offer is send-side only. Start with **AWS SNS**
if you want one API for both platforms, or **`.p8` + `node-apn` + FCM directly**
if you would rather not add a dependency for what is a small amount of code.

Sources: [OneSignal VoIP notifications](https://documentation.onesignal.com/docs/en/voip-notifications),
[Courier APNs integration](https://www.courier.com/docs/external-integrations/push/apple-push-notification),
[Amazon SNS platform applications](https://docs.aws.amazon.com/en_en/sns/latest/dg/mobile-push-send-register.html).
